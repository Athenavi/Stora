# Stora 开发路线图（修订版）

> 上一版把"补功能"当作主线。修订的原因是：功能面已经铺开（E2EE、同步、WebDAV、搜索、
> OCR、缩略图、转码、分享、团队、管理后台），但**刚把服务端第一次真正跑起来时，立刻
> 踩到三个真实问题**——数据库迁移追踪断代、注册接口只接受 form-encoded、密码策略缺失。
>
> 这说明当前瓶颈不是"缺功能"，而是**"没有一条被端到端验证过的路径"**。
> 估算单位为人日，均为粗估。

## 一、现状（规划的事实前提）

**真的能跑了**（本次首次达成）

- 后端在真实 PostgreSQL + Redis 上启动，`/api/health` → `{"status":"healthy"}`
- 前端 dev server 可访问（`vite --mode ssr`）
- 用户 `yang` 创建成功、登录返回 200
- **6 个新迁移首次在真实库上执行通过**（缩略图 / 应用密码 / 搜索索引 / 任务队列 / OCR / E2EE）
- 数据库 public schema 现有 31+ 张表

**已完成的功能面**

| 域 | 状态 |
|---|---|
| 内容搜索 | ✅ trigram GIN（中英文都能走索引）+ 前端搜索页（3 种模式 + 高亮）+ OCR 文本入库 |
| E2EE 私密空间 | ✅ 零知识：服务端只存密文与公开参数（PBKDF2 600k → masterKey → vaultKey → HKDF）；客户端 WebCrypto 实现 + 恢复码 + UI |
| 同步客户端 | 🟡 M1：`cmd/sync` 双向同步 + 冲突暂停询问 + 分片续传，零新依赖 |
| WebDAV | ✅ 应用专用密码 + `/dav`（**未在真实客户端验证过**） |
| 缩略图 | ✅ 任务表 + 轮询 worker + 端点 + 前端接入（PDF 首页缩略图未做） |
| 对象存储 | ✅ S3 驱动（AWS SDK v2 → RustFS）；**不作为发布阻断**（本地驱动可用） |
| 审计会话 | ✅ 写入 `audit_logs` / `user_sessions`（吊销不即时，见 P1） |
| 前端 lint | ✅ 168 → 0，`npm run build` 通过 |

**本次暴露的真实缺陷**（比"未实现的功能"更紧急）

| # | 问题 | 症状与位置 |
|---|---|---|
| 1 | **迁移追踪断代** | `schema_version` 里的记录名（`init_20260624_214042`）与迁移文件名（`20260625_init`）是两套命名 → CLI 把全部迁移判为未应用 → `migrate up` 撞已存在的表而失败。**新部署与升级必然踩到** |
| 2 | **注册接口只接受 form-encoded** | `Register` 用 `r.FormValue`（`internal/api/v2/auth/handler.go:35`）→ 按 REST 习惯发 JSON 会 400 |
| 3 | **大文件全内存** | `StoreHash` 与 `/sync/upload` 都是 `io.ReadAll` → GB 级文件 OOM（`pkg/storage/local.go`、`internal/api/v2/files/blocks.go`） |
| 4 | **限流可绕过** | 信任客户端 `X-Forwarded-For` → 登录爆破防护形同虚设 |
| 5 | **会话吊销不即时** | 无状态 JWT 的固有天花板；改密码/踢会话后旧 token 仍有效 |
| 6 | **密码策略缺失** | `123456` 能成功注册 |

## 二、核心判断（这份路线图的依据）

### 判断一：瓶颈是"验证"，不是"功能"

功能清单已经很宽，但**没有任何一条完整路径被真实跑过**。本次仅仅"启动 + 建用户"
就暴露了三个问题，说明"能编译 + 单元测试过"与"能用"之间还有很大距离。
继续加功能的边际收益，低于把已有功能验证到可用。

### 判断二："超越百度网盘/阿里云盘"不在同一维度竞争

主流网盘的护城河是**内容理解（AI 搜图、人脸、文档解析）+ 生态绑定**，
而这条护城河**建立在一个前提上：它们必须能看到你的内容**（审核要读、AI 要读）。

所以正面对标它们的 AI 功能是**劣势战场**（我们算力、数据量都不如）。
Stora 的结构性优势是它们**做不到**的三件事：

| Stora 能做到 | 主流网盘为什么做不到 |
|---|---|
| 零知识加密（E2EE） | 必须能读内容才能做审核与 AI，端到端加密与它们的商业模式直接冲突 |
| 数据不出内网（本地 AI） | 它们的 AI 必须在云端跑，本地算力不在它们的交付范围内 |
| 开放协议（WebDAV / S3） | 协议封闭是锁定用户的手段 |

**胜点 = 隐私 + 本地智能 + 开放 的组合**，而不是"功能数量更多"。
三者还能互相强化：E2EE 让"数据不出内网"有实际意义，本地 AI 让 E2EE 不等于"功能阉割"，
开放协议让用户不必把数据托付给单一产品。

### 判断三：个人优先，团队靠"协议"而非"功能"

个人用户要的是：**装上就能同步、搜得到、看得见、不怕丢**。
团队用户要的是：**权限、共享、审计**——而这些用 WebDAV/S3 接入既有工具（而非做一个
协作套件）成本低得多。所以团队能力应通过**开放协议**交付，而不是复刻一套钉钉/飞书。

## 三、P0：把一条完整路径真正跑通（先做，否则一切是空谈）

| 编号 | 任务 | 为什么必须先做 | 估算 |
|---|---|---|---|
| P0-1 | **修迁移追踪断代**：统一 `schema_version` 记录名与文件名，或写一个"历史对齐"迁移 | 新部署/升级必失败，是上线的硬阻断 | 0.5–1 |
| P0-2 | **浏览器端到端主流程**：登录 → 上传 → 缩略图 → 预览 → 搜索 → 分享 → 私密空间（加密上传/解锁） | 唯一能证明"能用"的手段；本次改动幅度很大（约 20 个前端文件） | 1–2 |
| P0-3 | **同步客户端 M1 真机跑一遍**：login → once → 改文件 → once → 制造冲突 | 代码写完了，但一次都没真跑过 | 0.5–1 |
| P0-4 | **WebDAV 真机验证**：Windows「映射网络驱动器」+ rclone | 唯一无法自动化、也最容易踩坑的一环 | 0.5–1 |
| P0-5 | **Docker 实测**：`docker build` 跑通 + 用镜像起一次 | Dockerfile 已补但从未构建过（本机 Docker daemon 当时未运行） | 0.5 |
| P0-6 | **注册接口接受 JSON**，并加上密码强度校验 | 前端按 REST 发 JSON 会 400；弱密码能注册 | 0.5 |

**P0 合计约 4–6 人日。** 做完这一轮，项目才真正处于"能部署、能被别人用"的状态。

## 四、P1：会咬人的技术债（做 P0 时顺路清）

| 编号 | 任务 | 说明 | 估算 |
|---|---|---|---|
| P1-1 | **大文件流式化** | `StoreHash` 改 `io.TeeReader` + 临时文件；`/sync/upload` 改为直接落盘。GB 级文件现在会 OOM，这是**功能可用性**问题不是优化 | 2–3 |
| P1-2 | 限流改读真实连接地址 | 不再信任 `X-Forwarded-For`（仅在可信代理后才启用） | 0.5 |
| P1-3 | 会话吊销即时化 | 引入 token 版本号或 `user_sessions` 校验（可接受"最多 1 个 token 有效期"的延迟，但要有明确窗口） | 2–3 |
| P1-4 | handler 层测试 | 现在 HTTP handler **零测试**，只有 `pkg/auth`、`pkg/storage`、`cmd/cli`、`cmd/sync` 有 | 8–12（分批） |
| P1-5 | CI 加 `gofmt -l` 与 `tsc --noEmit` 卡口 | 格式与类型刚修绿，**现在加卡口成本最低** | 0.5 |

## 五、P2：差异化纵深（护城河的下一层）

按"判断二"的框架排序，**每一条都必须是主流网盘做不到或不愿做的**：

| 编号 | 任务 | 为什么这是我们的战场 | 估算 |
|---|---|---|---|
| P2-1 | **E2EE 可用性**：加密分享、多设备解锁、密钥轮换、口令找回流程 | 现在 E2EE 只有"单个 vault 能用"，离"日常可依赖"还有距离；这是护城河的地基 | 8–12 |
| P2-2 | **本地语义搜索** | `pgvector` + 本地嵌入模型（或客户端嵌入）。**云端网盘也做语义搜索，但它们必须把你的文件传上云**；我们在内网做，这是 E2EE 兼容的 AI | 8–10 |
| P2-3 | **同步 M2/M3**：托盘常驻、选择性同步（占位文件） | 个人用户的"回不去"体验；M1 已验证骨架可行 | 10–14 |
| P2-4 | **本地照片智能**：场景/重复检测/人脸聚类 | 同 P2-2 的逻辑：商业网盘的照片 AI 必须上传原图 | 15–25（可分步） |
| P2-5 | **开放协议扩展**：S3 兼容网关（rclone / aws-cli 直连） | 让"开放"从 WebDAV 单点变成组合拳；团队用户可用既有工具接入 | 15–20 |
| P2-6 | 局域网快传 | 同网段直连，不经服务器；对应阿里云盘"快传"，且更私密 | 8–12 |

## 六、推荐路径

```
P0 验证与修复（4–6 人日）        ← 让当前成果真正可用、可部署
        │
        ├─► P1-1 大文件流式化（2–3）      ← 与 P0 同期做，因为它决定"能不能用"
        │
        ├─► P2-1 E2EE 可用性（8–12）      ← 护城河地基：先把差异化做扎实
        │        └─► P2-2 本地语义搜索（8–10）   ← 与 E2EE 组合成"隐私 + 智能"
        │
        └─► P2-3 同步 M2/M3（10–14，可并行）
```

**为什么先 P2-1（E2EE 可用性）而不是继续补通用功能**：
通用功能（相册、分享、预览、转码）主流网盘都已成熟，追平它们的收益是"不落后"；
而 E2EE + 本地智能是**它们结构上做不到**的，做强了才是"超越"。

**如果只有一个人在做**：P0 → P1-1 → P2-1 → P2-2。

## 七、明确不做（以及为什么）

| 项 | 原因 |
|---|---|
| 云端 AI 能力（人脸、场景、语义）**上传到服务器** | 与 E2EE 定位直接冲突；要做就在客户端/本地做（见 P2-2、P2-4） |
| CRDT 实时协作 | 与已有 WOPI/Collabora 在线编辑重叠，20–30 人日换来的增量最小 |
| 复刻一套团队协作套件（IM/审批/日程） | 团队需求用 WebDAV/S3 接入既有工具更划算（见判断三） |
| 移动端原生 App | Web + WebDAV 已覆盖大部分场景；等同步客户端验证了需求再评估 |
| 多租户 / 计费 / 订阅 | 与"自托管、无会员墙"的定位冲突 |
| PDF 首页缩略图 | 需引入 poppler，收益低于成本（现用文件图标兜底） |
| MinIO 适配 | 已归档并转向 AGPL 独占，明确不再支持（见 `docs/deployment-rustfs.md`） |
