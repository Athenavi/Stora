## 1. 缩略图与预览管线（P0，个人体验的门面）

### 目标
- 相册/网格视图不再加载原图：200 张图首屏传输 **< 5 MB**。
- 生成失败不影响上传主流程。

### 现状锚点
- 前端已在调用 `GET /api/v2/files/preview/{id}/thumbnail?size=1024`（`PreviewPanel.tsx`、`drive/index.tsx`、`photos/index.tsx`），**后端没有该端点**——请求被 `/files/preview/{id}/{filename}` 的 `{filename}` 段吞掉，返回的是**全尺寸原文件**。
- `file_items.thumbnail_url`（text）字段已存在，从未写入。
- 上传落点：`UploadFile`、`CompleteUpload`、`SyncUpload(Assign)`、`ShareFileUpload`、`WOPI PutFile` 都会更新 `file_items.file_path`/`file_hash`。

### 设计与契约

**新端点**（放进认证组，与 `DownloadFile` 同级做归属校验）：

```
GET /api/v2/files/{id}/thumbnail?size=sm|md|lg     # 缺省 md
响应：image/jpeg 或 image/webp，带 ETag 与 Cache-Control: private, max-age=86400
未生成时：202 Accepted + Retry-After: 2（前端退化为占位图，不阻塞列表渲染）
永久不可生成（不支持的格式）：404
```

**新表**：

```sql
create table file_thumbnails (
    id           bigint generated by default as identity primary key,
    file_id      bigint      not null references file_items on delete cascade,
    size         varchar(8)  not null,            -- sm|md|lg
    width        integer     not null,
    height       integer     not null,
    storage_path text        not null,            -- 走 StoreHash 的 content-addressed 路径
    created_at   timestamp   not null default now(),
    unique (file_id, size)
);
create index idx_file_thumbnails_file_id on file_thumbnails (file_id);
```

**生成队列**：新增 `thumbnail_jobs (id, file_id, attempts, status, last_error, created_at, updated_at)`，复用既有 `CleanupScheduler` 的“定期扫表 + 后台 goroutine”模式（不要引入外部队列）。

**生成器**：

| 类型 | 手段 | 备注 |
|---|---|---|
| image/* | 标准库 `image` + `golang.org/x/image/draw`（CatmullRom） | 新依赖，与已有 `x/crypto` 同源，可接受 |
| video/* | 既有 ffmpeg：`-ss 1 -frames:v 1 -vf scale=...` | 复用 `exec.Command` 模式 |
| application/pdf | 需要 poppler/mupdf，**本期不做**（前端用文件图标兜底） | 标注为后续项 |

**尺寸**：`sm=256`、`md=512`、`lg=1024`（长边，等比；只放大不缩小）。

### 改动清单
- `migrations/2026xxxx_thumbnails.sql`（新表，含 `-- UPGRADE/-- DOWNGRADE` 段）。
- `internal/api/v2/files/thumbnail.go`（新）：`ThumbnailHandler`，`Get`（读表+鉴权+缓存头）、`enqueue`、`processJob`。
- `internal/api/v2/files/handler.go`：`UploadFile`/`UpdateFileContent` 成功后 `enqueue`。
- `internal/api/v2/files/upload.go`：`CompleteUpload` 成功后 `enqueue`。
- `internal/api/v2/files/blocks.go`：`SyncUploadAssign`/`SyncUploadComplete` 成功后 `enqueue`。
- `cmd/server/main.go`：注册端点 + 启动生成 worker。
- 前端：把三处 `thumbnail?size=N` 统一为 `?size=lg|md|sm`；<img> 加 `loading="lazy"`；补占位图与失败回退。

### 风险与取舍
- **不引入 libvips**：纯 Go 缩放对大图（>50 MP）CPU 较高；用并发上限（如 2）与尺寸上限（长边 > 8192 直接跳过）兜住。
- 生成失败必须静默降级（前端显示图标），**绝不能**让上传失败。

### 验收
- 相册页 200 张图的 `Content-Length` 总和 < 5 MB。
- 上传 1 GB 视频后 10 s 内出现 `md` 缩略图。
- `go test ./internal/api/v2/files -run Thumb` 覆盖：尺寸计算、不放大、不支持格式返回 404。

**估算**：3–5 人日。

## 2. 对象存储后端（S3 兼容；RustFS 为推荐实现）

> **状态：第一版已实现** —— `pkg/storage/s3.go`（AWS SDK v2 + `transfermanager`）、
> `ObjectKey`/`ValidateKey` 键契约、配置项、启动时按驱动分派、`pkg/storage/s3_test.go`。
> **未实现**：`HashKnownDriver` 快路径（唯一已知 hash 的调用链 `SyncUpload` 本身已把内容
> 读入内存，收益有限，等实测有需求再加）、`stora-cli storage migrate`（当前用 `mc mirror` 代替，
> 见 `docs/deployment-rustfs.md`）。

> **MinIO 不再支持**（已归档，且转向 AGPL 独占路线）。推荐 **RustFS**：Apache-2.0、S3 兼容、
> 可直接作为 MinIO 的迁移目标（34.8k stars，默认 9000 端口，`RUSTFS_*` 环境变量配置）。
> Ceph RGW、AWS S3、阿里 OSS 等任何 S3 兼容端点同属支持范围——我们按**协议**对接，不按厂商绑定。

### 目标
- `STORAGE_DRIVER=s3` 时，全部上传/下载/分享/WOPI/同步流程通过，无需改任何 handler。

### 现状锚点
- `pkg/storage/storage.go` 的 `Driver` 接口已抽象好（`Store`/`StoreHash`/`Retrieve`/`Delete`/`Exists`/`URL`）。
- `cmd/server/main.go` 硬编码 `storage.NewLocalDriver(...)`。
- `config.Config` 已有 `S3Endpoint/Region/Bucket/AccessKey/SecretKey`，**无人读取**。

### 设计与契约

- 依赖：**AWS SDK for Go v2**（`aws-sdk-go-v2/config`、`credentials`、`service/s3`、`feature/s3/manager`）。
  - **不用 `minio-go`**：它虽是可用的 S3 客户端，但与本项目"不绑定 MinIO"的定位冲突；AWS SDK v2 中立、长期维护，且对任意 S3 兼容端点都适用。
- 新增 `pkg/storage/s3.go`：`S3Driver` 实现 `Driver`。
- **不自动建桶**：RustFS/S3 均不自动创建 bucket。启动时 `HeadBucket`，失败即 `log.Fatal` 并提示建桶方式（自动建桶会在 endpoint 拼错时静默建出空桶，掩盖配置错误）。
- **关键点：`StoreHash` 要在未知长度下流式写对象并算出 SHA256**，三条路径：
  1. 已知 hash（上传/同步等本来就算过 hash 的调用链）→ 走可选接口 `HashKnownDriver`，单次 PUT。
  2. 未知 hash → `manager.Uploader` 分片传到**临时 key**，算完 hash 后 `CopyObject` 到最终 key 并删临时对象。
  3. 统一由 `manager.Uploader` 承担大文件分片（Concurrency 默认 4，可配）。
- 建议的接口微调（向后兼容，不破坏 LocalDriver）：

```go
// 新增：希望调用方在已知内容 hash 时直接给出，避免二次写入
type HashKnownDriver interface {
    StoreHashKnown(reader io.Reader, hash string) (relPath string, err error)
}
```

  调用链：`UploadFile`/`CompleteUpload`/`SyncUploadAssign` 本来就已经算出 `fileHash`，可以走快路径；`WOPI PutFile`、`ShareFileUpload` 等未知场景走临时对象路径。

- `Retrieve`：`GetObject` 返回的 `Body`（`io.ReadCloser`），调用方无感。
- `URL`：`presign.GetObject` 生成预签名 URL（默认 15 分钟）。
- key 校验：拼 key 前复用与 `LocalDriver` 相同的校验（拒绝含 `..`/绝对路径的 key），两端行为必须一致。
- path-style：非 AWS 端点默认 `UsePathStyle: true`（自托管最稳），可配关闭。

### 配置（`.env.example` 增补）

```bash
STORAGE_DRIVER=s3                 # local | s3
S3_ENDPOINT=http://rustfs:9000    # RustFS 默认端口 9000
S3_REGION=us-east-1               # 多数自托管实现忽略该值，但 SDK 需要一个
S3_BUCKET=stora
S3_ACCESS_KEY=...
S3_SECRET_KEY=...
S3_FORCE_PATH_STYLE=true
S3_PRESIGN_DOWNLOAD=false
```

> RustFS 侧凭据由它自身的 `RUSTFS_*` 环境变量配置（见其部署文档）；Stora 只消费标准 S3 端点 + AccessKey/SecretKey。

### 改动清单
- `go.mod`（+aws-sdk-go-v2 四件套）、`pkg/storage/s3.go`（新）、`pkg/storage/storage.go`（可选接口 + key 校验）。
- `cmd/server/main.go`：按 `cfg.StorageDriver` 分派；`store` 变量类型仍是 `storage.Driver`。
- `pkg/config/config.go`：`StorageDriver` 校验 + `S3ForcePathStyle` + `S3PresignDownload`。
- `.env.example`：按上文补齐，并注明"MinIO 不再支持，推荐 RustFS"。
- `docs/deployment-rustfs.md`（新）：RustFS 最小部署（docker run / compose）+ 建桶命令 + 与 Stora 的对接参数。
- `pkg/models/file.go`：`storage_driver` 的注释 `local/s3/minio` → `local/s3`。
- 迁移工具（后置）：`stora-cli storage migrate --from local --to s3`（逐对象 `StoreHashKnown`），本期只留 TODO 与文档。

### 风险与取舍
- 对象键前缀沿用 `hash[:2]/hash[2:]`，与本地一致 → 迁移是纯拷贝，语义不变。
- 预签名 URL 会让下载绕过应用层审计；**默认关闭**，由管理员显式开启。
- 单 bucket 起步，不做 per-user bucket（增加成本与运维面）。
- RustFS 版本迭代快：只依赖标准 S3 API 子集（PutObject/GetObject/HeadObject/DeleteObject/CopyObject/HeadBucket），**不使用任何厂商扩展**，以便随时切到 Ceph/AWS/OSS。

### 验收
- `pkg/storage/s3_test.go`：`STORAGE_TEST_S3=1` 时才执行的真环境用例，验证 `StoreHash` 幂等（同内容二次调用不新增对象）、`Retrieve` 往返一致、生成的 key 与 `LocalDriver` 完全一致。
- 手工：`STORAGE_DRIVER=s3` 指向 RustFS，走完上传/下载/分享/WOPI 编辑/同步上传。

**估算**：5–8 人日（含 AWS SDK v2 的两条写入路径与真环境验收）。

## 3. WebDAV 网关（差异化第一张牌）

### 目标
- macOS「连接服务器」、Windows「映射网络驱动器」、`rclone mount` 三种客户端可直接读写。

### 为什么值得先做
商业网盘**不提供**这一层；而个人用户已经习惯用它接 Infuse/Jellyfin/Finder。这是自托管最容易形成“回不去”的差异点。

### 设计与契约

- 库：`golang.org/x/net/webdav`（无新增第三方依赖，`x/` 系列与现有依赖同源）。
- 挂载点：`/dav`（保留 `/webdav` 别名），由 `cmd/server/main.go` 在**认证之外**单独挂载（WebDAV 用自己的认证）。
- **认证方式**：Basic Auth + **应用专用密码**（新表 `app_passwords`）。理由：Finder/Windows 只支持 Basic/Digest；用主密码风险过大，专用密码可单独吊销（Nextcloud 的成熟做法）。

```sql
create table app_passwords (
    id           bigint generated by default as identity primary key,
    user_id      bigint       not null references users on delete cascade,
    name         varchar(100) not null,
    password_hash varchar(128) not null,   -- bcrypt
    last_used_at timestamp,
    created_at   timestamp    not null default now()
);
```

- `webdav.FileSystem` 实现映射到现有模型：

| WebDAV 操作 | 实现 |
|---|---|
| `Stat` | 按路径解析出 `file_items` 行（复用 `validateFolderPath` + `resolvePath`） |
| `Readdir` | 复用 `GetFolderChildrenByPath` 的查询 |
| `Mkdir` | 复用 `CreateFolderByPath` |
| `OpenFile(写)` / `PUT` | `StoreHash` 落对象 + **写 `file_versions` 一个新版本**（与 `WOPI PutFile` 行为对齐） |
| `RemoveAll` | 软删（进回收站），与 Web 端一致 |
| `Rename` | 复用 `RenameFile`/`MoveFile` 语义 |

- 锁：`webdav.NewMemLS()`。**Ceiling**：多实例部署时锁不共享，同一文件并发编辑可能冲突 → 代码内 `ponytail:` 注释标明“升级路径为 Redis 锁”。
- 配额：越过 `total_storage` 时对 PUT 返回 `507 Insufficient Storage`。
- 审计：每次 PUT/DELETE 写一行 `audit_logs`（顺带点亮这张一直空着的表，见第 5 节）。

### 改动清单
- `go.mod`（+`golang.org/x/net`，可能已是间接依赖）、`internal/webdav/handler.go`（新包）、`internal/webdav/fs.go`（新）。
- `migrations/*_app_passwords.sql`（新表）。
- `internal/api/v2/auth/handler.go`：新增「创建/吊销应用专用密码」端点（`POST/DELETE /api/v2/auth/app-passwords`）。
- `cmd/server/main.go`：`r.Mount("/dav", webdavHandler)`。
- 前端 `settings` 页：应用密码管理 UI（列表 + 新建 + 吊销）。
- `docs/deployment-nginx.md`：补 WebDAV 的 nginx 配置（`client_max_body_size`、大文件超时、`PROPFIND` 等方法放行）。

### 风险与取舍
- **Windows 客户端兼容性**是最常见的坑（PROPFIND 深度、`Win32` 属性），必须用真实 Windows 验证一次。
- 大文件 PUT 会长时间占用连接 → 需与本次已拆分的长超时路由对齐（WebDAV 路径也走 600 s 档）。

### 验收
- 三种客户端各完成一次：列目录 → 上传 100 MB → 下载 → 改名 → 删除。
- 上传后的文件在 Web 端可见且带版本记录。

**估算**：8–12 人日。

## 4. 传输并发与断点续传（低风险高感知）

### 现状锚点
- 前端 `upload-utils.ts` 的分片上传是**串行 `await`**；后端 `UploadChunk` 已支持乱序、已有 `chunk_hash` 去重与 `received_chunks` 计数（并发安全）。

### 设计
- 前端加并发池（默认 3，可在设置里调 1–6），失败分片指数退避重试 3 次，进度按“已完成分片字节数”聚合。
- 断点续传：`InitUpload` 已返回 `received_chunks` → 续传时跳过已收分片（前端已有分支，需接上并发池）。
- 后端**无需改动**（乱序与幂等已具备）——这正是先做它的原因。

### 改动清单
- `frontend-qwik/src/components/upload/upload-utils.ts`（并发池 + 重试 + 进度聚合）。
- `frontend-qwik/src/components/ui/TransferQueue.tsx`（多任务并发时的进度展示）。

### 验收
- 100 Mbps 链路：上传 1 GB 文件耗时接近理论上限（对比现状应提升 2–3 倍）。
- 中途断网 10 s 后恢复，已上传分片不重传。

**估算**：3–4 人日。

## 5. 顺带点亮两张空表（低成本、企业侧必要）

个人优先不等于放弃团队能力，以下两项成本极低且已在 schema 中：

1. **`audit_logs` 写入**：登录/登出、文件删除与彻底删除、分享创建与吊销、权限变更、WebDAV 写入 → 统一通过一个 `audit.Log(ctx, action, resource, detail)` 辅助函数。
2. **`user_sessions` 写入**：登录时插一行、登出置 `is_active=false`、`RevokeSession` 才能生效（当前该接口因无数据而永远返回 404）。

**验收**：登录一次后 `/api/v2/auth/sessions` 返回该会话；删除一个文件后 `/api/v2/admin/audit-logs` 能看到记录。
**估算**：3–5 人日。

## 6. 同步客户端（设计纲要，个人用户的长期核心）

服务端已就绪（`/sync/changes`、`/sync/upload`、`/sync/upload/assign`、`/sync/upload/session`），缺的是客户端。**本阶段只定里程碑，不排详细设计**，因为它是 15–25 人日的独立工程。

| 里程碑 | 内容 | 验收 |
|---|---|---|
| M1 只读镜像 | Go + SQLite 本地状态 + `fsnotify` 监听 → 单向增量上传；服务端变更单向下载 | 1 万文件首次同步完成，之后变更 500 ms 内触发 |
| M2 双向 + 冲突策略 | 冲突时保留双方（`name (conflict 2026-07-06).ext`），本地记录决策 | 断网 10 分钟后恢复，无数据丢失 |
| M3 选择性同步 | 占位文件（Windows CFAPI / macOS FileProvider 或退化为 `.stora-placeholder`） | 用户可只同步部分目录 |

**技术选型**：Go（与本仓库同语言，可复用 `pkg/storage` 与 hash 逻辑），Windows 优先（`docs/windows-app-guide.md` 已存在）。

## 7. 执行顺序与依赖

```
阶段 0（文档止损，0.5–1d）
   │
   ├─► 1 缩略图（3–5d）────► 前端相册/网格收益立刻可见
   ├─► 4 传输并发（3–4d）──► 纯前端，可与 1 并行
   └─► 2 S3 驱动（5–8d）───► 部署形态解锁
                                  │
                                  └─► 3 WebDAV（8–12d）──► 依赖 2 提供的对象存储（本地存储也能跑，但 S3 下更有意义）
                                          │
                                          └─► 5 审计/会话（3–5d，可随时插入）
                                                  │
                                                  └─► 6 同步客户端（15–25d，独立轨道）
```

**建议的第一个 sprint**：阶段 0 + 4（传输并发）。两者合计约 4–5 人日、风险最低，且第一个是消除决策噪音、第二个用户立刻能感知。

**第二个 sprint**：1（缩略图）+ 5（审计/会话）。

**第三个 sprint**：2（S3）→ 3（WebDAV）。
